# 大熊动医新 PRD 对比与系统改造清单

> 日期：2026-05-07  
> 来源文档：`/Users/combo/MyFile/my-data/projects/common/dxdy-design/大熊动医.docx`  
> 对比对象：当前 dxdy 演示系统、`req.md v2.1`、现有小程序与管理后台代码  
> 结论：新 PRD 将系统从“通用医检电商 demo”进一步明确为“宠物血包行业交易 + 履约 + 检测追溯 + 代理运营”系统。

## 0. 当前技术背景更新

### 0.1 `packages/shared` 不再作为真实业务基准

用户已确认：现有 `packages/shared` 部分后续不要了。小程序和后台已经接入云开发，后续需求分析、改造设计和验收应以 CloudBase 环境中的云函数、数据库集合、权限规则、存储和实际接口为准。

因此，本文档中涉及 `packages/shared` 的内容只能作为历史 demo 参考，用于理解旧系统曾经覆盖过哪些页面和 mock 逻辑，不能作为后续实现的真实数据模型或服务边界。

后续改造基准应调整为：

- 小程序端：以 `wx.cloud`、小程序云函数和云数据库读写为准。
- 后台端：以后台调用的 CloudBase 接口、后台云函数、云数据库和云存储为准。
- 数据结构：以云数据库集合结构、云函数入参/出参、权限规则和已有真实数据为准。
- 文档与任务拆分：不再要求改造 `packages/shared`，而应拆到云函数、云数据库集合、前端调用层、后台调用层和权限规则。

### 0.2 CloudBase MCP 环境基准

项目根目录存在项目级 `.mcp.json`，CloudBase MCP 配置通过项目级环境变量指定云环境。后续应以项目级 `.mcp.json` 的 `CLOUDBASE_ENV_ID` 为准，而不是以全局 MCP 自动绑定环境为准。

当前项目级目标环境：

- `CLOUDBASE_ENV_ID=cloudbase-d4gwpsm7gcc59b6fc`
- 本地小程序 `packages/miniprogram/miniprogram/app.ts` 初始化的云开发环境也是 `cloudbase-d4gwpsm7gcc59b6fc`。

说明：此前通过全局 MCP 探测到的 `clo-test-4g8ukdond34672de` 是全局级自动绑定环境，只能作为误差来源提示，不应作为本项目后续设计、数据查询或改造判断的依据。

后续通过 CloudBase MCP 查询云函数、数据库集合、权限规则和存储资源时，应确保使用项目级 `.mcp.json` 加载的环境。

### 0.3 后续梳理方式调整

下一轮深入设计时，应优先补充以下 CloudBase 实况：

- 拉取关键云函数详情或下载云函数代码，尤其是 `wx-goods`、`wx-order`、`wx-coupon`、`wx-tracker`、`wx-express`、`admin-goods`、`admin-order`、`admin-marketing`、`wx-pay-callback`。
- 确认真实业务集合、索引和权限规则是否存在于项目级环境 `cloudbase-d4gwpsm7gcc59b6fc`。
- 整理云函数 API 清单，包括 action、入参、出参、错误码和权限判断。
- 整理云数据库集合设计，包括索引、安全规则和关键状态字段。
- 再基于真实 CloudBase 结构拆分改造任务。

## 1. 已确认保留事项

### 1.1 待支付订单改价必须保留

虽然新 PRD 没有重点展开“后台待支付订单改价”，但该能力来自 `req.md v2.1`，且已在当前系统中实现基础演示能力，因此后续不能删除。

保留规则：

- 仅待支付订单可改价。
- 只能降价，不能高于客户原下单金额。
- 改价权限应由角色权限控制。
- 改价后应通知客户重新确认支付。
- 改价后应重置支付超时计时。
- 改价操作必须进入不可删除操作日志。
- 改价后应同步影响订单实付金额和代理商/业务员提成基数。

后续改造时，改价应与新增的订单金额拆分模型兼容，包括商品金额、优惠金额、运费、加急费用、退款金额、提成基数等。

## 2. 差异总览

当前系统已具备客户、业务员、制单员、小程序商城、订单、退换货、商品管理、用户管理、系统配置、操作日志等 demo 能力。

新 PRD 相比当前系统主要新增或强化以下方向：

- 角色语义从“业务员”偏向“代理商”，并明确代理商实名认证、推广、提成、提现闭环。
- 医院客户和个人客户的购买权限更严格，尤其血包商品只能由已认证医院客户购买。
- 商品体系新增商品类型、血包卡券、加急血包、检测/服务类商品、协议、配送范围和预约规则。
- 血包检测追溯成为核心行业能力，需要一包一码、二维码查询、检测报告管理和权限控制。
- 订单金额结构需要拆分，支持优惠、运费、加急费用、退款、发票金额、提成基数。
- 售后规则需要区分普通商品和血包商品，血包仅支持质量问题售后。
- 新增卡券购买、赠送、领取、兑换、核销、过期、作废等完整流程。
- 新增发票申请能力。
- 通知能力从 mock 通知扩展为微信服务号通知 + 后台站内通知。
- 新增活动、拉新、积分商城、会员充值、评论审核等运营能力。
- 新增埋点与数据化运营能力。

## 3. 现有系统需要改造的模块

### 3.1 用户与角色体系

现状：

- 当前代码已有客户、业务员、制单员、后台管理员角色。
- 客户分为 `institution` 和 `personal`。
- 后台角色包含客服、商品管理员、系统管理员。

需要改造：

- 将产品语义统一为“代理商”，代码层可短期兼容 `salesperson`，但前端文案、后台展示、文档应逐步统一。
- 代理商需要独立实名认证流程，包含姓名、手机号、身份证号、银行卡信息、推广区域或合作信息。
- 个人客户永远不需要实名认证，但不能购买血包类商品。
- 医院客户必须通过机构认证后才能购买血包类商品并展示医院价。
- 同一手机号仅允许注册一个主账号。
- 同一医院资质不允许重复认证多个医院主体，特殊情况需后台人工处理。
- 代理商绑定关系原则上客户不可自行解绑，后台变更需记录原因。
- 代理商查看客户信息时需要脱敏展示。

### 3.2 商品体系

现状：

- 当前商品模型支持分类、规格、库存、机构价、个人价、可见范围、退换货规则、是否血包、检测信息 URL。
- 商品管理后台可配置机构价、个人价、上下架和可见范围。

需要改造：

- 增加 `productType`，至少覆盖：普通商品、血包商品、加急血包、血包卡券、检测/服务类商品。
- 增加是否支持预约、预约规则、预约时限、配送范围、冷链/温控要求。
- 增加是否支持加急、加急费用、加急配送区域、加急最早预约时间、加急费用是否可退。
- 增加商品协议配置，血包定制类商品下单前必须勾选协议。
- 增加销量展示配置，由后台决定是否展示销量。
- 增加血包售后边界：血包类商品仅支持质量问题售后，不支持无理由退换。
- 当前 `testInfoUrl` 不足以承载血包追溯，需要独立检测报告/血包码模型。

### 3.3 购买权限与下单校验

现状：

- 前端已有机构专区、血包预约入口和价格展示。
- 商品列表会根据客户类型过滤商品。
- 下单服务层主要创建 mock 订单，对购买权限缺少强校验。

需要改造：

- 未登录用户不可下单，应引导登录。
- 未认证医院客户可买普通商品，但不可购买血包类商品。
- 个人客户可买普通商品，但不可购买血包类商品。
- 已认证医院客户可购买血包类商品和普通商品。
- 血包商品进入详情或下单时，必须给出明确限制提示。
- 下单时需要校验登录状态、认证状态、购买权限、库存、配送范围、预约时限、协议勾选。
- 购物车结算时也必须逐项校验商品权限和库存，不能只在列表或详情页限制。

### 3.4 订单与金额模型

现状：

- 当前订单分为普通订单和预约订单。
- 金额模型只有原始金额、实付金额和改价记录。
- 订单状态较简化。

需要改造：

- 订单类型扩展为普通订单、预约订单、卡券订单、卡券兑换订单等。
- 金额字段需要拆分：商品总金额、优惠金额、实付金额、运费、加急费用、退款金额、发票金额。
- 提成基数应独立计算，扣除退款金额，不包含加急费用，卡券兑换订单不计提成。
- 支付回调需要幂等处理，避免重复生成订单或重复提成。
- 普通订单状态需要覆盖：待支付、已支付/待确认、待指派、待发货、已发货、配送中、已签收、已完成、售后中、已关闭。
- 预约订单状态需要覆盖：待支付、待确认、已确认、备货中、已发货、已完成、已取消、异常。
- 订单应支持异常处理、客服备注、导出和售后关联记录。
- 继续保留待支付订单改价，并使其兼容新金额模型。

### 3.5 预约与加急血包

现状：

- 当前已有血包预约页面，主要面向已认证机构客户。
- 预约信息包含日期、地点、联系人、联系电话。

需要改造：

- 预约时间需要精确到小时。
- 预约应校验区域、预约时限、库存和配送范围。
- 加急血包应作为订单附加费用或服务费处理，不能简单通过人工改价表达。
- 加急费用不计入代理商提成。
- 加急费用是否可退需要可配置。
- 制单员需要能看到预约时间、备注、备货要求和加急标识。

### 3.6 制单员履约

现状：

- 小程序端已有制单员待处理订单、订单列表、订单详情、录入物流。
- 后台订单管理可指派制单员。

需要改造：

- 制单员接单后应能标记备货中。
- 快递单号需要格式校验。
- 无法发货时可标记异常并填写原因。
- 发错快递单号时后台可修改，必须记录操作人、时间、原因。
- 换货发货任务和普通发货任务都应进入制单员待办，并标记换货类型及原订单号。
- 后台不设置独立制单员角色，系统管理员可执行制单员相关操作。

### 3.7 退换货与售后

现状：

- 当前已有退换货记录、审核、寄回物流、验货和换货发货任务的基础 mock。

需要改造：

- 售后类型需要覆盖退货退款、换货、仅退款。
- 售后申请需要支持问题描述和图片/视频凭证。
- 售后状态需要覆盖：待审核、审核驳回、待客户寄回、待平台收货、待验货、验货通过、验货不通过、退款中、换货发货中、售后完成、售后关闭。
- 普通商品按平台售后规则执行，售后期限默认 7 天。
- 血包类商品仅支持质量问题售后，不支持无理由退换。
- 质量问题售后需关联血包编号、检测报告、物流温控或异常签收记录。
- 退货成功后扣回代理商提成。
- 换货成功后按换货后实际商品和金额重新计算提成，多退少补。
- 已提现提成发生扣回时，从后续可结算提成中抵扣。

### 3.8 代理商推广、提成与提现

现状：

- 当前小程序已有业务员推广二维码、客户列表、佣金概览、提现申请 mock。
- 当前共享服务中已有提成记录和提现记录。

需要改造：

- 业务员前端文案需要逐步改为代理商。
- 代理商必须实名认证通过后才能推广和提现。
- 推广二维码需要统计扫码访问、注册客户、认证客户、下单客户。
- 客户绑定规则：首次二维码注册后绑定代理商，重复扫码不自动覆盖。
- 绑定关系变更只能后台操作，并记录原因。
- 代理商工作台需要展示推广客户数、有效客户数、客户订单数、客户下单金额、待结算提成、可提现提成、已提现提成、提成明细、提现记录、退换货影响记录。
- 提成产生节点改为客户支付成功后生成待结算提成。
- 订单完成后进入售后冻结期，默认 7 天，过期转为可提现。
- 提成比例、冻结期、最低提现金额由后台配置。
- 加急费用、卡券兑换订单不计入提成。
- 促销订单是否计提成由后台活动规则控制。
- 提现申请需客服或财务审核，提现失败需记录原因并退回余额。

### 3.9 血包卡券

现状：

- 当前系统没有卡券模型和兑换流程。

需要新增：

- 代理商购买血包卡券。
- 代理商选择赠送医院客户。
- 医院客户领取卡券。
- 医院客户兑换血包并填写预约时间、地址、联系人。
- 系统校验区域、时限、库存和卡券有效性。
- 兑换成功生成预约订单。
- 卡券状态至少包含：未赠送、已赠送、已领取、已兑换、已核销、已过期、已作废。
- 卡券兑换订单不计入代理商提成。

### 3.10 血包检测追溯

现状：

- 当前商品只有 `testInfoUrl` 字段，无法支持一包一码和完整报告管理。

需要新增：

- 血包编号模型，一包一码。
- 二维码扫码和手动输入血包码查询入口。
- 查询入口包括商品详情页、首页检测信息栏目、订单详情页、血包实物二维码、售后申请页。
- 检测信息字段至少包括：血包编号、商品名称、批次号、血型、采集日期、检测日期、有效期、检测项目、检测结果、储存条件、运输要求、报告附件、关联订单。
- 客户扫码只查看基础检测信息和是否合格。
- 客服和管理员可查看完整检测信息、关联订单和内部备注。
- 检测报告修改需要权限控制和操作日志。
- 检测报告由系统管理员上传，无需审核，普通用户不可修改。

### 3.11 发票

现状：

- 当前订单备注中可填写发票要求，但没有发票申请模型和流程。

需要新增：

- 订单详情中的发票申请入口。
- 发票字段：发票类型、抬头、税号、邮箱、订单编号、开票金额、申请状态。
- 发票由人工处理。
- 发票金额需要与订单金额、退款金额保持一致。

### 3.12 通知体系

现状：

- 当前有 mock 通知数据和未读查询能力，但缺少完整触发流程和外部渠道。

需要改造：

- 通知渠道使用微信服务号，后台保留站内通知。
- 通知场景至少覆盖：客户支付成功、预约订单支付成功、订单被指派、订单发货、认证提交、认证通过/驳回、售后申请、售后审核结果、客户填写寄回物流、提现申请、提现结果。
- 通知失败需要记录并支持重发。
- 新订单、售后、提现等后台通知应能形成待办。

### 3.13 管理后台

现状：

- 当前后台已有商品、订单、退换货、用户、账号、角色、系统配置、日志和仪表盘。

需要改造：

- 用户管理需要支持医院认证、代理商认证、代理商银行卡、客户脱敏、代理关系查看。
- 商品管理需要支持商品类型、预约规则、加急规则、售后规则、协议、销量展示、卡券商品。
- 订单管理需要支持更多状态、待指派、异常订单、加急标识、导出、发票、检测报告关联。
- 退换货管理需要支持凭证、验货结果、质量问题判定、检测报告关联、换货任务创建。
- 提成管理应独立成后台模块，包括提成比例、冻结期、最低提现金额、提成明细、扣回记录、提现审核、提现导出。
- 检测报告管理应独立成后台模块。
- 卡券管理应独立成后台模块。
- 通知/待办中心应独立或集成到仪表盘。
- 数据看板需要新增代理商贡献排行、售后率、预约订单量、加急订单量、提成支出等指标。

### 3.14 运营活动

现状：

- 当前已有积分、钱包、充值档位字段，但功能闭环不足。

需要新增或后续迭代：

- 一分钱促销。
- 拉新活动。
- 满额提示与复购引导。
- 血包卡券购买、赠送、兑换。
- 积分体系和积分商城。
- 会员充值。
- 商品评论审核。
- 商品销量展示配置。
- 血型匹配工具。
- 血包使用视频教学。
- 客服企业微信/微信绑定。

其中，一分钱促销和拉新活动需要防刷规则，包括手机号、设备、医院资质、收货地址等维度。

### 3.15 埋点与数据统计

现状：

- 当前系统没有明确埋点体系。

需要新增：

- 客户行为埋点：首页访问、商品列表访问、商品详情访问、点击购买、点击预约、提交订单、支付成功、售后申请、检测信息查询、客服点击。
- 代理商数据埋点：二维码访问、客户注册、客户认证、客户首单、客户复购、提现申请。
- 后台统计指标：新增客户数、新增医院认证数、新增代理商数、支付订单数、支付金额、退款金额、售后率、预约订单量、加急订单量、提成支出、代理商贡献排行。
- 后续支持页面访问路径、商品转化率、复购率、活动转化率。

## 5. 关键验收关注点

- 个人客户无需实名认证，但不能购买血包类商品。
- 未认证医院客户不能购买血包类商品，但可以购买普通商品。
- 已认证医院客户能看到医院价并购买血包类商品。
- 待支付订单改价仍可用，并且只能降价、需权限、记日志、通知客户。
- 加急费用不计入代理商提成。
- 卡券兑换订单不计入代理商提成。
- 血包售后仅允许质量问题，且能关联检测报告、批次、物流或凭证。
- 代理商首次绑定关系不可被后续扫码覆盖。
- 所有关键人工操作都有日志，包括改价、退款、扣回、提现审核、检测报告修改、绑定关系变更。
- 支付回调、退款、提成生成需要幂等。
