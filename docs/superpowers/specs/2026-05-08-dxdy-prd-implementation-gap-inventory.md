# 大熊动医 PRD 功能实现 Gap 盘点

> 日期：2026-05-08  
> 来源文档：`/Users/combo/MyFile/my-data/projects/common/dxdy-design/大熊动医.docx`  
> 对照范围：`packages/miniprogram` 小程序页面与云函数、`packages/admin` 后台页面与 CloudBase 服务、`packages/miniprogram/cloudbase` 本地集合规则/索引配置、现有项目文档。  
> 统计口径：`基本实现` 表示已有可用页面/云函数/后台操作并覆盖 PRD 主流程；`部分实现` 表示已有入口或基础数据读写，但规则、状态、权限、后台处理或验收细节未闭环；`未实现` 表示未发现对应页面、云函数、集合模型或后台能力。

## 1. 结论

本次从 PRD 中拆出 96 个可验收功能点。

| 状态 | 数量 | 占比 | 说明 |
| --- | ---: | ---: | --- |
| 基本实现 | 32 | 33.3% | 能跑通基础链路，但多数仍是 MVP/模拟支付/简化状态。 |
| 部分实现 | 30 | 31.3% | 有页面、字段或云函数雏形，但未满足 PRD 完整规则。 |
| 未实现 | 34 | 35.4% | 没有对应业务闭环或核心模型。 |
| Gap 合计 | 64 | 66.7% | `部分实现 + 未实现`，即还不能按 PRD 验收的功能。 |

因此，如果按“没有达到 PRD 验收标准”计算，当前系统还有 64 个功能点存在 gap；其中 34 个是完全未实现，30 个是部分实现但需要补齐。

## 2. 主要依据

已发现的实现依据：

- 小程序页面已覆盖客户首页、分类、购物车、订单、售后、发票、物流、检测查询、医院认证、代理申请/提现/客户/订单、制单员待办/订单/发货等入口：`packages/miniprogram/miniprogram/app.json`。
- 关键云函数已覆盖下单、模拟支付、改价、指派、发货、医院认证审核、代理商审核、售后审核、提现、发票处理等：`packages/miniprogram/cloudfunctions/*`。
- 小程序服务层已接 CloudBase 集合和云函数，包括 `orders`、`returns`、`invoices`、`test_reports`、`commission_records`、`withdrawals` 等：`packages/miniprogram/miniprogram/services/index.ts`。
- 后台已有商品、订单、退换货、财务、用户、账号、角色、系统、日志和仪表盘页面：`packages/admin/src/app/(admin)`。
- 本地 CloudBase 配置已声明 `users`、`orders`、`returns`、`invoices`、`test_reports` 规则/索引，但规则覆盖仍偏基础：`packages/miniprogram/cloudbase`。

重要限制：

- 当前支付是 `payOrder` 云函数模拟状态更新，未接真实微信支付回调。
- 后台多数页面是基础运营台，不是 PRD 中完整的客服/财务/管理员协作后台。
- 代理商相关代码仍大量沿用 `salesperson` 命名，业务语义未完全统一。
- CloudBase 集合和安全规则尚未覆盖 PRD 中全部数据模型，尤其卡券、活动、埋点、通知、检测报告管理、操作审计细粒度权限。

## 4. P0 Gap：交易与履约验收前必须补齐

### 4.1 购买权限与实名认证强规则

当前状态：部分实现。

已有：

- `createOrder` 云函数会校验 `product.isBloodPack`，限制血包仅已认证医院客户购买。
- 注册支持 `customerType`，医院认证页和 `reviewVerification` 云函数已存在。

Gap：

- 个人客户永远无需实名认证、且不能买血包的规则未在所有入口统一校验，购物车/商品详情/预约入口仍需逐项确认。
- 同一手机号仅允许一个主账号，目前只按 `{ phone, role: 'customer' }` 检查，未覆盖代理商、制单员、后台账号等跨角色唯一性。
- 同一医院资质不得重复认证多个主体，未发现资质编号/营业执照唯一校验。
- 代理绑定关系不可自行解绑、后台变更需记录原因，当前仅有 `boundSalespersonId` 基础绑定字段和查询聚合。

建议补齐：

- 在 `createOrder`、购物车结算、预约下单、商品详情按钮统一走同一套购买权限函数。
- 为手机号、医院资质、代理绑定关系建立唯一性/变更审计规则。

### 4.2 商品模型不足

当前状态：部分实现。

已有：

- 商品集合和后台商品管理存在，支持分类、库存、个人价/机构价、上架状态、血包标识等基础能力。
- 小程序列表和详情能按分类、关键词、可见范围展示。

Gap：

- PRD 的 `product_type` 未完整覆盖普通商品、血包商品、加急血包、血包卡券、检测/服务类商品。
- 预约规则、配送范围、区域预约时限、冷链/温控要求没有完整商品级配置。
- 是否支持加急、加急费用、加急配送区域、加急最早预约时间、加急费用是否可退未闭环。
- 下单协议配置和血包定制协议勾选未形成强校验。
- 销量展示开关未见完整后台配置和前台展示联动。

建议补齐：

- 扩展 `products` 模型和后台商品表单，先覆盖 PRD P0 字段：`productType`、`supportReservation`、`reservationRule`、`deliveryScope`、`supportUrgent`、`urgentRule`、`agreement`、`saleDisplayConfig`。

### 4.3 订单金额与状态模型不足

当前状态：部分实现。

已有：

- `createOrder` 支持普通订单和预约订单。
- `payOrder` 模拟支付后流转到 `pending_shipment` 或 `pending_confirmation`。
- 后台订单页支持筛选、改价、指派制单员、发货、取消/确认等基础操作。
- `adjustOrderPrice` 限制待支付订单只能降价并写日志。

Gap：

- 订单金额只有 `pricing.originalAmount/actualAmount/priceLog`，缺少 PRD 要求的商品总额、优惠金额、运费、加急费用、退款金额、发票金额、提成基数。
- 支付回调未接真实微信支付，幂等、防重复提成、防重复状态更新未完整实现。
- 普通订单状态未覆盖 `已支付/待确认`、`待指派`、`配送中`、`已签收`、`售后中`、`已关闭` 的完整流转。
- 预约订单状态未覆盖 `备货中`、`已取消`、`异常` 等完整状态。
- 库存扣减/释放未形成支付、取消、退款的一致事务。

建议补齐：

- 先重构订单金额结构，保留旧字段兼容。
- 将支付成功、库存、提成生成做成幂等云函数或回调处理器。
- 明确普通订单和预约订单的状态机，后台按钮只允许合法流转。

### 4.4 制单员履约不完整

当前状态：部分实现。

已有：

- 小程序有制单员待处理、订单、详情、物流页。
- `assignOrderToClerk` 和 `clerkShipOrder` 云函数已实现基础指派和发货。
- `clerkShipOrder` 对血包订单要求包装类型、冷链方式、箱内温度，并记录物流日志。

Gap：

- 快递单号格式校验仍较弱，未按快递公司规则校验。
- 制单员无法发货时标记异常并填写原因的闭环不足。
- 后台修改快递单号虽要求 `modifyReason`，但后台发货弹窗只传公司和单号，没有暴露冷链、重量、箱温、修改原因等字段。
- 换货发货任务没有明确进入制单员待办。
- 客户侧物流还不是实时第三方物流同步，主要读取订单内 `shipping.logistics`。

建议补齐：

- 后台和制单员端统一使用完整 `clerkShipOrder` 参数。
- 增加 `shipment_tasks` 或在订单/售后中建独立履约任务，覆盖普通发货、预约发货、换货发货、异常发货。

## 5. P1 Gap：代理、售后、行业能力

### 5.1 售后规则未达到血包业务要求

当前状态：部分实现。

已有：

- `createReturn` 支持退货退款、仅退款、换货，支持描述、凭证、退款金额上限和重复申请限制。
- `reviewReturn` 支持审核、客户寄回、收货质检、退款、换货发货、完成等基础状态。
- 后台退换货页面存在。

Gap：

- 售后申请期限 7 天未按订单完成时间强校验。
- 血包仅支持质量问题售后、不支持无理由退换的规则未在云函数中完整判断。
- 售后状态命名与 PRD 不完全一致，缺少 `待平台收货`、`待验货`、`验货通过/不通过` 等清晰业务节点展示。
- 客户填写寄回物流的独立动作与通知不完整。
- 质量问题需关联血包编号、检测报告、物流温控、异常签收记录，当前售后模型只保留基础凭证和 `verificationResult`。
- 退货扣回提成、换货重算提成、已提现扣回抵扣后续可结算提成未闭环。

建议补齐：

- 在 `createReturn` 和 `reviewReturn` 增加商品类型、售后期限、质量问题、检测报告和提成调整校验。
- 售后完成时触发订单、退款、提成状态的幂等更新。

### 5.2 代理商推广和提成仍是基础版

当前状态：部分实现。

已有：

- 代理商申请、审核状态、推广、客户、客户详情、代理订单、提成、提现、银行卡等页面/云函数已存在。
- `submitAgentApplication`、`reviewAgentApplication`、`saveAgentBankCard`、`requestWithdrawal`、`reviewWithdrawal` 已覆盖基础流程。

Gap：

- 审核通过后专属推广二维码的生成、保存、分享、扫码统计未形成完整闭环。
- 推广绑定规则只见 `boundSalespersonId`，缺少首次扫码注册绑定、防重复覆盖、后台改绑原因记录。
- 代理商不能查看客户敏感信息完整明文，当前服务层有 `maskPhone` 工具，但后台/代理详情脱敏策略未统一审计。
- 提成比例、冻结期、最低提现金额虽有系统配置字段，但提成计算仍多处固定或简化，例如 `createOrder` 默认按 20% 预估。
- 提成产生节点、冻结期转可提现、退货扣回、换货重算、已提现抵扣未形成自动状态机。
- 提现失败原因和退回可提现余额只覆盖驳回路径，不等于完整打款失败处理。

建议补齐：

- 设计 `agent_relations`、`commission_records`、`withdrawals` 的正式状态机。
- 将提成生成从 `createOrder` 中拆到支付成功后的幂等结算服务。

### 5.3 血包检测追溯只是查询雏形

当前状态：部分实现。

已有：

- 小程序有检测查询/报告页。
- 服务层支持按 `test_reports.code` 或 `batchNo` 查询。
- 本地配置中有 `test_reports` 索引和只读规则。

Gap：

- 一包一码的血包编号模型没有完整创建、绑定商品/批次/订单/售后的流程。
- 商品详情、首页检测栏目、订单详情、实物二维码、售后申请页五个入口未全部贯通。
- 检测信息字段缺少完整结构化模型，包括采集日期、检测日期、有效期、检测项目列表、详细指标、储存条件、运输要求、报告附件、关联订单、内部备注等。
- 客户只能看基础检测信息、客服/管理员看完整报告的权限分层未实现。
- 后台检测报告上传/修改/操作日志未实现独立模块。

建议补齐：

- 新增后台检测报告管理模块和血包码管理模型。
- 将售后质量问题和订单血包明细关联到 `test_reports`。

### 5.4 管理后台能力仍不完整

当前状态：部分实现。

已有：

- 后台已有仪表盘、商品、订单、退换货、财务、用户、账号、角色、系统配置、日志页面。
- 后台已能调用部分云函数处理订单、售后、提现、发票、医院认证、代理商审核。

Gap：

- 客服审核中心还不是统一待办中心，医院认证、代理认证、售后、寄回验货、提现申请分散在页面中。
- 商品管理缺少 PRD 商品类型、预约、加急、协议、卡券、检测报告关联等字段。
- 订单管理缺少导出、异常订单、客服备注、售后关联深度视图、加急标识、检测报告关联。
- 提成管理没有独立模块，无法配置比例/冻结期/最低提现、查看扣回、导出提现。
- 卡券管理、检测报告管理、通知/待办中心未实现。
- 数据看板缺少代理商贡献排行、售后率、预约订单量、加急订单量、提成支出等。

建议补齐：

- 不要继续把所有财务能力塞进 `finance`，应拆出 `commission`、`withdrawal`、`invoice` 的业务视角。
- 新增后台 `reports`、`coupons/cards`、`notifications/tasks` 模块。

## 6. P2 Gap：完全未实现或后续运营能力

### 6.1 血包卡券完整缺失

当前状态：未实现。

未发现以下能力：

- 代理商购买血包卡券。
- 代理商赠送医院客户。
- 医院客户领取卡券。
- 医院客户兑换血包并填写预约履约信息。
- 校验区域、时限、库存、卡券有效性。
- 兑换生成预约订单。
- 卡券状态：未赠送、已赠送、已领取、已兑换、已核销、已过期、已作废。
- 卡券兑换订单不计入代理商提成。

建议优先级：P1 或 P2，取决于卡券是否进入第一期业务闭环。

### 6.2 营销活动、积分、会员体系未闭环

当前状态：未实现。

已有一点基础字段：

- 注册用户默认写入 `points` 和 `wallet` 初始结构。
- 系统类型中有积分、充值、卡券相关历史字段。

未实现：

- 一分钱促销。
- 拉新活动。
- 满额提示与复购引导。
- 积分来源、积分消耗、积分商城。
- 会员充值和会员权益。
- 活动资格防刷，包括手机号、设备、医院资质、收货地址维度。
- 活动订单是否计入提成的后台配置和结算规则。
- 商品评论审核、商品销量展示后台配置。
- 血型匹配工具、血包使用视频教学。

建议优先级：P2。不要在订单金额模型稳定前做复杂营销，否则会增加财务和提成对账风险。

### 6.3 通知和埋点体系缺失

当前状态：未实现/部分实现。

已有：

- 有 `notifications` 集合迹象和小程序/后台若干待办式页面，但未形成统一通知服务。

Gap：

- 微信服务号通知未实现。
- 后台站内通知没有统一触发、阅读、失败重试、重发机制。
- PRD 通知场景未覆盖：支付成功、预约支付、订单指派、发货、认证提交/结果、售后申请/结果、寄回物流、提现申请/结果。
- 客户行为埋点未实现：首页访问、商品列表、详情、购买、预约、下单、支付、售后、检测查询、客服点击。
- 代理商埋点未实现：二维码访问、客户注册、认证、首单、复购、提现申请。
- 后台统计指标缺少系统化采集口径。

建议优先级：通知 P1，埋点 P3。通知影响业务处理及时性，埋点可在核心闭环稳定后补。

## 7. 非功能 Gap

### 7.1 安全与权限

当前状态：部分实现。

Gap：

- 身份证号、银行卡号、手机号等敏感信息没有统一加密/脱敏策略。`saveAgentBankCard` 直接保存银行卡号。
- 后台权限主要是角色菜单和部分云函数权限，尚未形成字段级/操作级权限矩阵。
- `test_reports` 规则允许登录用户读取全部报告，未按基础/完整报告分权。
- 重要操作日志已有基础记录，但覆盖不完整，缺少绑定关系变更、检测报告修改、退款、提成扣回、系统参数变更等完整审计。

### 7.2 稳定性

当前状态：部分实现。

Gap：

- 支付回调幂等未完整实现。
- 物流同步失败重试未实现。
- 通知失败记录和重发未实现。
- 售后、提现、提成状态仍有越级流转风险，需要正式状态机和并发保护。

### 7.3 可配置性

当前状态：部分实现。

Gap：

- 系统配置有基础字段，但商品价格、医院价/个人价、加急费用、提现门槛、提成比例、冻结期、售后期限、预约时限、活动规则并未全部被业务云函数读取和强制执行。

## 8. 推荐补齐顺序

### 第一批：保证交易闭环可验收

1. 统一用户/角色/认证/购买权限规则。
2. 扩展商品模型：商品类型、预约、配送、加急、协议、售后规则。
3. 重构订单金额模型和状态机。
4. 接真实支付回调或至少完成支付成功幂等处理。
5. 完成库存扣减/释放、订单取消/关闭、自动确认收货。
6. 完成制单员异常发货、修改物流、换货任务。

### 第二批：保证代理和售后闭环可验收

1. 代理二维码生成、扫码绑定、防覆盖、后台改绑审计。
2. 提成规则配置、支付成功生成、冻结期、可提现、扣回、换货重算。
3. 售后 7 天期限、血包质量问题限制、寄回物流、验货、退款/换货、提成联动。
4. 提现失败原因和余额退回。
5. 后台统一审核/待办中心。

### 第三批：补行业能力

1. 血包一包一码和检测报告后台管理。
2. 检测查询权限分层和售后关联。
3. 加急血包费用、区域、时效、退款规则。
4. 血包卡券购买、赠送、领取、兑换、核销。

### 第四批：补运营和数据化

1. 微信服务号通知和后台站内通知。
2. 一分钱促销、拉新、防刷。
3. 积分、积分商城、会员充值。
4. 商品评论审核、销量展示配置。
5. 埋点、转化、复购、代理排行和活动效果看板。

## 9. 需要进一步确认的点

- PRD 中“本期 MVP”包含血包卡券、管理后台、检测追溯和基础通知，但“后续迭代”又包含卡券/活动/积分等运营能力。建议产品侧明确血包卡券是否进入第一期。
- 当前系统是否需要保留“业务员/salesperson”代码命名，还是在下一轮直接迁移到 `agent`。
- 真实支付和微信服务号通知是否已有外部商户号、服务号、模板消息配置。
- 检测报告由谁维护：系统管理员手工上传，还是实验室系统同步。
- 后台是否需要导出订单/提现/发票，如果需要，应明确导出格式和字段脱敏规则。
